## Background: how Changesets works in this repo

The repo uses `@changesets/cli` (the tool behind changesets.dev). The flow is:

1. A contributor adds a file in `.changeset/<slug>.md` with YAML frontmatter
   declaring the bump type (`patch` / `minor` / `major`) for the package
   `tumble-code`, plus a markdown summary.
2. `.changeset/config.json` sets the rules: `fixed: [["tumble-code"]]` keeps
   the single package on one version line; `commit: false` means the CLI does
   not commit on its own; `changelog: "./changelog-config.js"` formats each
   summary line as a bullet.
3. The canonical version lives in `src/package.json` (the root `package.json`
   has `name: "tumble-code"` but no `version` field). The npm script
   `changeset:version` copies root `CHANGELOG.md` into `src/`, runs
   `changeset version` (which bumps `src/package.json` and rewrites
   `src/CHANGELOG.md`), then copies `src/CHANGELOG.md` back to root.
4. On CI, `.github/workflows/changeset-release.yml` runs `changesets/action`
   after a PR with a changeset merges to main. The action consumes pending
   `.changeset/*.md` files, bumps the version, and opens a "Changeset version
   bump" PR (bot `R00-B0T`), which is then auto-approved and merged.

## Decision: reset to 1.0.0

The user decided to start Tumble Code versioning at `1.0.0`, treating the
rebrand as a new tool rather than a continuation of the 3.x line.

The normal `changeset version` bump math cannot express a reset from `3.53.1`
to `1.0.0` (a `major` bump from 3.53.1 yields 4.0.0). This is a one-time
editorial reset, so the changelog section and the version number are written by
hand. After this commit the normal per-change changeset flow resumes: new work
adds `.changeset/*.md` files and the CI bot produces version-bump PRs as usual.
