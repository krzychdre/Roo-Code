# WS-D rules/objective audit

This is the deliverable the WS-D section of `ai_plans/2026-08-24_dsh-adoption-implementation-plan.md`
asks for: a sentence-by-sentence verdict on `src/core/prompts/sections/rules.ts` and
`objective.ts`, recording which single-tool sentences moved into a tool's native schema
description, which were deleted as already covered there, and which stayed because they
concern several tools or general behavior.

## Method

A sentence "concerns exactly one tool" when following it requires calling that tool, or when
it constrains only that tool's arguments or result handling. Those move next to the tool, in
dsh style: one short imperative line inside the tool's schema description. A sentence is
deleted instead of moved when the tool description already says the same thing; the proof is
the quoted existing line. Everything else stays in the section.

## Deviations

1. **One shell-dependent execute_command line stays in rules.** The chaining operator and the
   PowerShell/cmd.exe utility note are computed from `getShell()` when the prompt is built,
   while `execute_command.ts` exports a static schema object. Moving them would require either
   freezing the shell at module load (`export const nativeTools = getNativeTools()`) or
   threading shell state through `getNativeTools` and `build-tools.ts`, both outside the plan's
   scope. The line was condensed instead.
2. **The MCP one-at-a-time rule stays in rules**, for the reason given in its table row.

## Cache effect

All of this is system-prompt prefix text plus tool-schema text, so the first request after the
upgrade pays a one-time prefix invalidation on providers with prompt caching. Steady state the
prefix is smaller by the amounts above.

## Candidates noted but not touched (outside plan scope)

- `capabilities.ts` bullet 3 restates `execute_command`'s description nearly verbatim
  ("Prefer to execute complex CLI commands over creating executable scripts"): roughly 500
  bytes of pure duplication.
- `capabilities.ts` bullet 2 re-explains `list_files`'s `recursive` parameter, which its schema
  already documents.
- `tool-use-guidelines.ts` item 2 contains a `list_files` sentence: "using the list_files tool
  is more effective than running a command like `ls` in the terminal".
- `objective.ts` item 2 still says "utilizing available tools one at a time", which contradicts
  the batching guidance in `rules.ts` and in `tool-use-guidelines.ts` item 3. Pre-existing
  contradiction, not a single-tool sentence.
- `output-efficiency.ts` contains a pre-existing em dash, which the repository convention
  forbids. Not introduced by this branch.

## Owed

The plan's WS-D gate is an agent-bench A/B on the Qwen 27B profile (malformed-call recovery
rate before and after). It needs a live model and has not been run.
